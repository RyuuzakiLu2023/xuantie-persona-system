# XTMEM 架构详解 (Architecture Specification)

## 1. 系统愿景与定位

在多 Agent 协同的工作流中，普遍存在两大痛点：
1. **多端孤岛与重复注入**：每个 Agent 维护独立的记忆碎片，跨端交互时无法有效共享，导致上下文冗余，严重击穿大模型的 Prompt Cache；
2. **闭眼抓药与虚假反馈**：传统的 RAG 检索往往“关键词相似就全盘塞给模型”，缺乏场景门控与置信度分层，且无法追踪模型是否真实引用了该事实。

**XTMEM 的定位**：
- **单一物理权威库**：以纯单机 SQLite (WAL) 为坚实底座，消灭沉重的图数据库与外部复杂中间件；
- **可见性隔离与多角色共治**：基于 `shared` / `private` / `shared-with` 权限与 Namespace 隔离，使多角色共用一库而不穿帮；
- **情境支援包（Support Bundle）**：从全量记忆无脑注入转向按需定制的最小事实切片，保护 Prompt Cache 并避免长上下文注意力稀释。

## 3. 核心设计机制

### 3.1 曝光五态状态机 (Exposure Lifecycle)
XTMEM 彻底解决了传统系统“捞过即当用过”的虚假记账问题：
- **`recalled`**：后台异步预取或 CLI 检索命中候选池；
- **`exposed`**：通过预算裁剪、冷却期与去重后，真实注入到大模型输入上下文中；
- **`cited`**：大模型在生成回复中明确引用了对应记忆锚点 `[m:mem-xxx]`；
- **`confirmed`**：用户在后续交互中对该事实给出了正向确认；
- **`corrected`**：用户指出该事实存在错误（连续两次被纠正的事实将自动移入冷宫退役）。

### 3.2 记忆分层与代谢 (Two-Tier Storage & Metabolism)
- **`raw` 层**：按会话窗口切片的原生对话正文（剔除冗余的工具调用和思考过程）；
- **`refined` 层**：经过旁路评判（Distill Judge）萃取出的高价值客观事实、规范与教训，带有不可伪造的 `source_ids` 原始血缘指针。
- **四道代谢闸门**：每日例行扫描过期、低置信与孤立记忆，保持检索池高信噪比。
